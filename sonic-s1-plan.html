Silicon program proposal

Sonic S1

A 20.6 mm² edge inference ASIC with a dedicated prefill engine, built for LiquidAI LFM2.5-8B-A1B

Most accelerator designs size the array for peak TOPS and discover afterwards that decode never uses it. S1 starts from the opposite fact: decode on this model is entirely memory-bound and needs 119 multiply lanes, while prefill is the only compute-bound phase and is the only latency a user actually feels. So the array is sized for time-to-first-token, runs two different dataflows, and power-gates the moment generation starts.

01 — Workload

Two models, one die

S1 targets LFM2.5-8B-A1B as its primary model and runs the dense LFM2.5-2.6B on the same silicon and the same firmware. Both are hybrid architectures — short causal convolution blocks interleaved with a small number of GQA attention layers — which is what makes them tractable on a small die.

The governing equation

Decode throughput is bandwidth ÷ 0.978 GB and nothing else. At 68.3 GB/s that is 119 G weights/sec, and batch-1 GEMV consumes one multiply per weight — so 119 lanes saturate the memory system. Every one of S1's 16,384 lanes beyond that exists for prefill. This single fact determines the entire floorplan.

02 — Prefill engine

The part that justifies custom silicon

Decode cannot be made faster by design — it is bandwidth divided by a constant, and any competent chip hits the same number. Prefill is different: it is compute-bound, it scales with the array, and it is the latency a user perceives as "the model is thinking." S1 is built around three mechanisms that a general-purpose NPU does not have.

1 — Dual-mode dataflow

Decode and prefill want opposite dataflows. In decode each weight is used exactly once, so the array must be weight-streaming and output-stationary. In prefill with a 2048-token chunk each weight is used hundreds of times, which is textbook weight-stationary systolic — load a tile once, stream activations through it.

S1 implements both on the same PEs, with the batch dimension as a continuum: 1 for decode, 8 for speculative verify, 2048 for prefill. The cost is roughly 15–20% area over a single-mode array in muxing and dual accumulator paths. The hard constraint is that mode-select logic must sit off decode's critical path — decode is the mode that ships in volume, and it must not pay for prefill's flexibility.

2 — Expert-major prefill scheduling

The naive schedule iterates tokens and gathers experts. For a chunk of 512 tokens, essentially all 32 experts are touched in every layer, so the chunk reads the entire 4,649 MB weight set. S1 inverts the loop:

for layer in 0..23:
    route all C tokens          # one 2048→32 GEMV per token
    for expert e in 0..31:
        load e's weights once   # 5.85 MB, contiguous
        GEMM against the ~C/8 tokens routed to e

Each expert is now read exactly once per chunk per layer, so prefill memory traffic is 4,649 MB ÷ chunk and falls linearly as the chunk grows:

Array size and chunk size are coupled through the routing, and this is the least obvious constraint on the chip. A systolic tile of edge T needs ≥T tokens per expert to fill, and tokens-per-expert is chunk ÷ 8 at top-4 of 32. Build a 16K-lane array with a 512-token chunk and it runs at 46% occupancy on ragged GEMMs. The 8 MB SRAM is not a luxury — it is what makes the array usable.

This is why the array is four independent 64×64 sub-tiles rather than one 128×128. The same 16,384 lanes, but short experts waste a quarter-sized pass instead of a full one: 0.888 against 0.805, at identical die area. A monolithic 128-edge array sits on the 0.80 gate with no margin.

Routing is also not uniform: some experts receive 20 tokens and others 400. The token-gather scheduler (0.25 mm²) handles ragged batches, packs short GEMMs together, and keeps the systolic array fed across the imbalance. This block is small in area and large in verification effort.

A 2K prompt answers in 213 ms — below the ~250 ms threshold where an interface stops feeling like it is waiting. Note the crossover at short prompts: the dense 2.6B is faster below ~512 tokens because the MoE must sweep all 32 experts regardless of how few tokens it is processing, while above 2K the MoE wins because only 1.69 B parameters are active. The firmware should pick the model by prompt length where both are resident — a scheduling decision, not a hardware one.

Long prompts remain the weak spot and the plan says so rather than hiding it. 32K takes 4 seconds, and 128K is not a supported interactive mode. Three mitigations, all sized at P1 rather than discovered at P3:

  • Prefix KV caching — persist and reuse the KV for a stable system prompt or document, turning the common repeat-query case into a near-zero TTFT.
  • Overlapped streaming prefill — begin emitting tokens before the whole prompt is consumed, where the application allows it.
  • Honest per-SKU context limits — publish the TTFT curve instead of quietly degrading.

Prefill burst power is ~2.9 W: 1.6 W of array plus ~0.9 W of memory plus SRAM traffic. It lasts 213 ms, and it is below decode's 3.8 W because compute-bound operation only runs the memory system at ~21 GB/s. The boost DVFS point exists to spend exactly this headroom.

A side benefit worth naming

A ×64 LPDDR5X interface plus power and ground is ~614 bumps, which needs ≥9.9 mm² of die at 110 µm fine-pitch C4 and ≥18.4 mm² at conventional 150 µm. At 20.6 mm² S1 is no longer bump-limited — it can use standard flip-chip packaging rather than requiring fine-pitch InFO. The prefill array partly pays for itself in package cost.

Node

14 nm LPP. The same design is roughly 36 mm² at 22 nm ULL; silicon cost is nearly a wash ($2.01/die at 14 nm on a $6,000 wafer against ~$1.90 at 22 nm on a $3,500 wafer) and 14 nm adds ~$4 M of mask cost. It wins on the two things that matter here: ~30% lower core power on a battery product, and enough density that the 16K-lane array is affordable at all. At 22 nm the array alone would be 11.5 mm² and the prefill story would not close.

Speculative decoding works on the dense model and barely works on the MoE

Liquid ships LFM2.5-8B-A1B-DSpark, a 328 M drafter, and publishes "~2.5× faster decoding with identical outputs". That figure is real and it does not transfer to S1 unchanged, because the two numbers measure different bottlenecks.

Its config.json matters: block_size = 9 and a dflash_config naming five target_layer_ids, so it emits a whole block of nine candidates in one pass while consuming the target's intermediate hidden states — not nine sequential passes. And at 327.7 M parameters against a 274.5 M body, it carries no vocab table of its own; the 128K × 2048 embedding is shared with the target. Both facts make it far cheaper than a naive drafter.

The MoE still erodes it. On a GPU, batch-1 decode is largely latency-bound — many small kernel launches against weights already in HBM — so speculation wins by collapsing nine launches into one. On S1 decode is purely bandwidth-bound, so speculation only helps if it moves fewer bytes. On a dense model it does, exactly. On an MoE a verify batch routes to many more experts than a single token, so much of the reuse is lost.

How much is lost is a measurement, not a derivation, and the difference is large. An independent-uniform-routing model predicts a batch of ten touches 23.6 of 32 experts. Traces captured from the real model — 16,104 routing decisions across all 22 MoE layers, see p3/capture_routing.py — show 14.7. Real sequences reuse experts; the uniform model assumes they do not, and understates the speculative gain by about 40%. Measured expert-load CV is 0.163 globally, so the aux-loss-free expert-bias balancing is working well.

So: budget 1.6× at 80% acceptance, rising to 2.4× at 90%. Liquid's published ~2.5× is within reach on S1 at high acceptance — it is not the ~1.1× the uniform bound suggested, and it is not free either. The remaining unknown is the acceptance rate itself on representative workloads, which needs the drafter checkpoint and is the last open P0 item. DSpark is lossless, so it costs nothing in quality; ship it, but keep the SKU table's headline on solo decode.

What the drafter demands of the hardware, all of which must be in the P2 RTL rather than discovered at P3: a hidden-state tap at target layers 2, 6, 10, 14 and 18 staged in SRAM (~102 KB at block 9); a second KV cache for the drafter's five dense attention layers, at 5.1 KB/token on top of the target's 6.14 — nearly doubling KV; 328 MB of resident drafter weights; mask token 125017 in the sampler path; a dynamic verify batch, because the confidence head varies the block length; and a second RoPE style, since the drafter sets rope_is_neox_style = false.

Where MoE does pay enormously

True concurrent batching — where every token is real rather than probabilistic — amortizes exactly as advertised: 2.3× at batch 8, 6.4× at batch 32, 25.5× at batch 128 (140 MB and 35 MB per token respectively). MoE is fundamentally a server-shaped architecture that happens to also beat dense by 1.6× at batch 1. If a multi-user SKU is ever on the roadmap, this is where its economics come from.

06 — Co-design

Model changes that would pay for themselves in silicon

S1 runs both published models unmodified. But the program has a rare advantage — the model and the chip can be specified together — and a handful of changes to the next LFM would buy more than any RTL optimization on this die. Listed by return.

1 — Convert three of six attention layers to sliding-window

The quadratic term is 32% of prefill at 32K and 66% at 128K, and it is the sole reason long-context TTFT is unshippable. Halving the number of full-attention layers roughly halves both the quadratic term and the KV cache. 32K TTFT drops from 4.0 s to ~2.7 s, KV at 128K drops from 805 MB to ~400 MB. The conv layers already carry local mixing, so the quality cost should be small — this is the highest-value change on the list.

2 — Add a shared always-on expert

Replace top-4-of-32 with one shared expert plus top-3 routed. The shared expert is dense, perfectly predictable traffic that can be prefetched a layer ahead and streamed sequentially, while the routed union shrinks. It moves bandwidth from the unpredictable gather path to the predictable stream path — the single most valuable thing you can do for a memory controller — and it slightly improves speculation, since part of every token's feed-forward is now shared across the verify batch.

3 — Factorize the LM head

The tied 128,000 × 2048 head is 15.5% of decode traffic — 139 MB read every token to produce one sampled ID. A low-rank factorization (2048 → 512 → 128K) or a 256-way cluster hierarchy would cut that to ~2%, worth ~13% end-to-end decode throughput for a modest quality cost. S1's LM-head unit already implements clustered pruning in hardware; a model trained for it would let the chip use the exact path rather than a bounded approximation.

4 — Train for routing stability

Add a loss term rewarding adjacent tokens for reusing experts. Every number in §05 improves: speculative gain, batching efficiency, and DRAM row locality on the gather path. This is a pure training-side change with no inference cost and no quality target of its own — and it is invisible to anyone who is not building the hardware.

5 — Keep every dimension a multiple of the systolic tile

Both current models already comply: 2048 = 16×128, 1792 = 14×128, 7168 = 56×128, 10752 = 84×128. Make it an explicit constraint rather than a happy accident, and pin the systolic tile edge at 128 so the model team has a fixed number to design against. A future moe_intermediate_size of, say, 1800 would cost 4% of the array to padding for no benefit.

6 — Widen the conv kernel before adding attention layers

Short conv is O(P) and nearly free on this chip — three cycles per layer per token, with state resident on die. Attention is quadratic and expensive. If the next model needs more mixing capacity, taking it from a 5- or 7-tap conv rather than a seventh attention layer is close to free in silicon. S1's conv unit already supports up to 7 taps for exactly this reason.

The one that would change the die

Everything above is a model change that S1 already accommodates. The one change that would justify a new floorplan is fewer, larger experts — say 8 experts top-1 at 4× the width. The sparsity ratio and therefore the bandwidth are identical, but each expert becomes a 23 MB contiguous read instead of 5.85 MB, DRAM efficiency improves, routing decisions drop 4×, and the ragged-GEMM scheduler becomes far simpler. Worth modelling at P1 before the model team freezes the next architecture.

07 — Numerics

Quantization sets the bandwidth, and the bandwidth is the product

Bit width is the highest-leverage decision on the program, so the recipe is frozen bit-exactly in a golden model before RTL starts. MoE adds one wrinkle: expert weights are individually less redundant than dense feed-forward weights, so INT4 transferring cleanly from the 2.6B needs testing, not assuming.

Routing divergence is a failure mode dense models don't have: a mis-routed token produces plausible output from the wrong expert, which no perplexity check reliably catches.

The business question this raises

S1 is 9.3% of the module's silicon and ~5% of its BOM; the memory sets both the price and the performance. Standalone, that is a hard product. The strong version of this program is IP, not a chip: a phone or robotics SoC vendor integrates the 20.6 mm² block onto their existing die and shares the LPDDR they already ship. Then the marginal cost really is 20.6 mm², the DRAM is free, and the economics work. Decide which business you are in before P4 — it changes the packaging, the DFT strategy, and the deliverable.

09 — Software

The compiler is half the program

  • Offline packer (Python): consumes the HF checkpoint, applies the §07 recipe, clusters the vocab, and emits a signed, AES-encrypted weight image laid out in the order the streamer walks it — DRAM row and bank order, each expert contiguous. Layout alone is worth 10–15% of achievable bandwidth.
  • Static schedule: a descriptor ring the RV32 core replays per token, with indirect descriptors for expert fetch whose base addresses the router patches at runtime. Emitted by the packer, checked into the firmware image.
  • Prefill scheduler: chunking, expert-major loop ordering, ragged-GEMM packing, and the decode↔prefill mode switch. The most intricate firmware on the chip and the one that determines whether the array is 90% or 25% occupied.
  • Model selection: with both models resident, choose by prompt length and quality target — the dense 2.6B is faster below ~512 tokens, the MoE above.
  • Expert prefetch: issue layer n+1's expert fetches during layer n's compute so the DRAM pipeline never drains.
  • Runtime: a small C library and a Linux/RTOS driver exposing an OpenAI-compatible completion API over the mailbox, plus a llama.cpp backend shim so day-one users have a familiar path.
10 — Flexibility

Three levels of "can it run the next model"

S1 running two different architectures on one die is the proof that this works — but only because it was designed in at P0. It cannot be retrofitted.

Level 1 — same architecture, new weights

A fine-tune, a v2.6 checkpoint, a domain adaptation. Free. The packer regenerates the image; firmware reflashes it and validates the versioned capability manifest on load.

Level 2 — same operators, different shapes

The 8B-A1B ↔ 2.6B case, and any future LFM. These are design rules, not features, and they cost ~10–15% on the non-array blocks:

  • Every dimension arrives in a descriptor. No block may hardcode d = 2048.
  • Datapaths process fixed 128-wide tiles and loop, matching the systolic edge.
  • head_dim 32/64/128 configurable; GQA ratio 1–8; conv kernel up to 7 taps.
  • RoPE θ is a register — 5e6 for the MoE, 1e7 for the dense model.
  • The SwiGLU PWL table is firmware-loadable, so SiLU, GELU and ReLU² are the same hardware.
  • Expert count, top-k, shared-expert presence and expert bias all programmable; num_dense_layers is a per-layer descriptor flag.
  • Ship the capacity. 8 GB runs both models; a future 7B dense at INT4 is 3.6 GB and still fits.

Level 3 — a genuinely different architecture

A Mamba-2 SSM, a diffusion LM, something not yet published. Over a 22-month program this is the real risk, and the answer is the 1.50 mm² programmable vector unit. A fully general GEMV/GEMM engine and streamer handle the ~90% of any transformer-family model that is matrix work, while an RVV-class core covers unusual elementwise and small-matrix ops. The conv and attention units become accelerators for the common case rather than the only path, and a new architecture runs at 60–70% of peak instead of not running at all — the difference between a two-year and a five-year product, for 7% of the die.

11 — Verification

Three references, and the model is the testbench

The failure mode in accelerator projects is a chip that closes timing and produces subtly wrong tokens. Guard with a layered reference chain, each layer bit-exact to the one above:

  1. PyTorch fake-quant model — establishes accuracy, produces the acceptance-gate numbers, dumps golden activations and golden routing decisions for every layer of both models.
  2. Bit-exact C golden model — accumulator widths, rounding modes, PWL segments, online-softmax ordering, top-k tie-breaking. This is the spec; the RTL implements it.
  3. RTL + cocotb differential harness — every unit against the C model on random and directed vectors; the full chip on real prompts, comparing per-layer tensors rather than just final tokens.
  4. FPGA emulation (VU19P class) — the whole 8.47 B model with real weights at ~50 MHz, then the 2.6 B on the same bitstream. Non-negotiable: every interesting bug lives in the interaction between DRAM scheduling, expert gather, and a 24-layer sequence.

Directed tests for the failures that actually happen: accumulator overflow at every reduction depth; enable signals asserted across two pipeline phases causing double accumulation; SRAM inferred as flip-flops instead of hard macros; the last group of a non-multiple-of-64 reduction; conv state at positions 0, 1, 2; RoPE at position 127,999; KV page-boundary crossing; speculative rollback mid-layer. Prefill- and MoE-specific: all 32 experts selected in one chunk; every token routed to the same expert; an expert receiving zero tokens; expert bias driving a routing tie; a router emitting an out-of-range index; the decode↔prefill mode switch mid-layer; a chunk that is not a multiple of the systolic tile; and a 24-hour soak decoding continuously against the C model with routing compared every token.

12 — Execution

Phases and kill gates

Sequenced because each phase's output is genuinely the next one's input: the numerics freeze gates the memory interface, which gates the floorplan, which gates tapeout.

  1. P0

    Numerics and routing freeze

    Weeks 1–8 · 2 ML engineers

  2. P1

Sweep array width against TTFT, chunk size against SRAM, systolic occupancy against routing imbalance, expert prefetch depth. Model the fewer-larger-experts variant.     Gate ≥ 65 tok/s at 4K context on SKU B; TTFT ≤ 250 ms at a 2K prompt; systolic occupancy ≥ 80% under measured routing imbalance; DRAM efficiency ≥ 85% of peak; defended power estimate.

  3. P2

    Unit RTL and automated PPA loop

    Weeks 12–30 · 4–5 RTL engineers

    Dual-mode array, streamer with expert gather, router and token-gather scheduler, attention engine, conv, vector, LM head, programmable vector unit — each with a cocotb differential bench against the C model, each in an automated Yosys/OpenROAD PPA loop from its first commit. Hierarchical accumulators from the start. SRAM as explicit hard-macro instantiations. Every Level-2 parameterization rule enforced by a lint check, not a convention.

    Gate Every unit bit-exact vs. C model; array closes 1 GHz with ≥ 15% slack in both dataflow modes; both models pass on the same RTL.

  4. P3

    Integration and FPGA bring-up

    Weeks 26–46 · full team

    NoC, RV32 sequencer, firmware, descriptor ring, indirect expert fetch, prefill scheduler, mode switching. Port to a VU19P-class board with real DDR. Run the full 8.47 B model end to end, then the 2.6 B on the same bitstream. Everything before this is a hypothesis.

    Gate Both models generating coherent text on FPGA; per-layer tensors and routing match the C model; measured TTFT within 20% of the P1 model.

  5. P4

    Physical design

    Weeks 40–62 · 3 PD engineers + foundry partner

    Commercial flow on the real PDK. PHY hardening and signal integrity, floorplan, CTS, timing closure across PVT, power grid and IR analysis for the array's burst current, DFT insertion and ATPG, signoff DRC/LVS/antenna.

    Gate Clean signoff, ≥ 98% stuck-at coverage, IR drop < 5% VDD under prefill burst, power within 15% of the P1 model.

  6. P5

    Tapeout and bring-up

    Weeks 62–96

    MPW shuttle first if budget is tight, full mask set if not. Test board, characterization across voltage and temperature, silicon-versus-FPGA correlation, firmware tuning against real DRAM behaviour.

    Gate Silicon within 10% of FPGA-projected throughput and TTFT at target power. Only then discuss a shrink or a second die.

Kill criteria — worth agreeing to in advance

Stop at P1 if modelled SKU B throughput lands below 45 tok/s at 4K context, or power exceeds 5 W, or TTFT at a 2K prompt exceeds 400 ms. Any of those means an off-the-shelf mobile NPU plus a good llama.cpp port beats this chip, and the honest move is to say so at week 14 rather than week 90. Stop at P0 if routing agreement cannot be brought above 99.5% at 4 bits — a chip that silently routes to the wrong expert is worse than no chip.
